= New Command Processing Infrastructure

The primary objective of this Google Summer of Code project was to migrate Apache Fineract's existing write APIs from the legacy `JsonCommand`-based architecture to the new typed Command Processing Infrastructure.

The new infrastructure introduces a modern, type-safe execution model inspired by the principles of Command Query Responsibility Segregation (CQRS). Rather than passing generic JSON throughout the application, every write operation is represented by dedicated request and response models together with strongly typed commands and command handlers.

This redesign improves compile-time safety, simplifies validation, reduces manual parsing, and establishes a clear separation between API resources, command dispatching, and business services.

== Architectural Overview

The new command processing framework divides the responsibility of processing a write request into several independent components.

----
                 HTTP Request
                      │
                      ▼
              REST API Resource
                      │
                      ▼
             Typed Request DTO
                      │
                      ▼
        Command<RequestType>
                      │
                      ▼
          CommandDispatcher
                      │
                      ▼
      CommandHandler<REQ, RES>
                      │
                      ▼
            Business Service
                      │
                      ▼
          Typed Response DTO
                      │
                      ▼
               HTTP Response
----

Each component has a single responsibility, resulting in cleaner architecture and significantly improved maintainability.

== Request DTOs

Every write operation begins with a dedicated request object.

Instead of passing generic JSON through the system, incoming requests are immediately mapped to strongly typed Java classes representing the exact structure expected by the operation.

Typical request DTOs include:

* GroupCreateRequest
* CalendarCreateRequest
* ClientAddressCreateRequest
* FamilyMemberUpdateRequest

Each request model clearly defines:

* Required fields
* Optional fields
* Data types
* Validation rules

Using dedicated request objects makes the API self-documenting and enables compile-time verification of request structures.

== Jakarta Bean Validation

Validation is now declared directly on request DTOs using Jakarta Bean Validation annotations.

Typical examples include:

[source,java]
----
@NotNull
private Long officeId;

@NotBlank
private String name;

@Positive
private Long clientId;
----

Instead of manually checking values inside business services, validation is performed automatically before business logic is executed.

This approach provides:

* Consistent validation
* Reduced boilerplate code
* Improved readability
* Centralized validation rules

== Typed Commands

Once a request object has been created, it is wrapped inside a typed command.

[source,java]
----
Command<GroupCreateRequest>
----

Unlike the previous architecture, commands now explicitly describe the type of request they carry.

This provides compile-time guarantees regarding the payload being processed and eliminates the need for generic JSON handling.

Each command represents exactly one business operation.

Examples include:

* GroupCreateCommand
* CalendarUpdateCommand
* ClientIdentifierDeleteCommand

Commands act purely as transport objects and contain no business logic.

== Command Dispatcher

The CommandDispatcher serves as the central routing component of the new architecture.

Instead of REST resources invoking service implementations directly, they submit typed commands to the dispatcher.

The dispatcher is responsible for locating the appropriate command handler for the supplied command type and delegating execution.

This centralization provides several benefits:

* Uniform command execution
* Cleaner REST resources
* Reduced coupling
* Easier extensibility

REST resources therefore become significantly smaller because they no longer contain orchestration logic.

== Command Handlers

Business operations are implemented inside dedicated command handlers.

Each handler is responsible for processing exactly one command type.

Typical handler structure:

[source,java]
----
public class GroupCreateCommandHandler
    implements CommandHandler<
        GroupCreateRequest,
        GroupCreateResponse> {
    ...
}
----

Unlike the legacy implementation where large service classes handled multiple responsibilities, command handlers focus exclusively on coordinating a single business operation.

Their responsibilities typically include:

* Receiving validated requests
* Invoking business services
* Returning typed responses

This improves modularity and makes the execution flow significantly easier to understand.

== Business Services

Business services continue to contain the core domain logic of Apache Fineract.

However, unlike the legacy architecture, services now operate on fully validated, strongly typed request models instead of generic JSON objects.

Typical service responsibilities include:

* Business rule validation
* Entity creation
* Database updates
* Domain interactions
* Transaction management

Because request parsing and validation have already been completed, service implementations become smaller and focus entirely on business behaviour.

== Typed Responses

Instead of returning the generic `CommandProcessingResult`, every operation now returns its own response model.

Examples include:

* GroupCreateResponse
* CalendarUpdateResponse
* ClientAddressCreateResponse

Typed responses provide several advantages:

* Better API documentation
* Stronger client code generation
* Clear operation semantics
* Improved readability

Each response explicitly communicates the outcome of the corresponding business operation.

== Separation of Responsibilities

One of the major architectural improvements introduced by the new framework is the clear separation between infrastructure concerns and business logic.

[cols="1,3",options="header"]
|===
|Component
|Primary Responsibility

|REST Resource
|Accept HTTP requests and dispatch commands

|Request DTO
|Represent validated request data

|Command
|Wrap the request payload

|Command Dispatcher
|Locate the appropriate handler

|Command Handler
|Coordinate business execution

|Business Service
|Implement domain logic

|Response DTO
|Represent the operation result
|===

This separation makes the architecture easier to understand, test, and extend.

== Benefits of the New Architecture

The migration to the typed command processing framework introduces several significant improvements over the legacy implementation.

* Strong compile-time type safety.
* Elimination of manual JSON parsing.
* Automatic request validation.
* Cleaner REST resources.
* Smaller and more focused service implementations.
* Dedicated handlers for each business operation.
* Strongly typed API responses.
* Improved maintainability.
* Better support for API client generation.
* Clearer architectural boundaries.
* Simplified onboarding for future contributors.

== Relation to My Google Summer of Code Project

The work completed during Google Summer of Code 2026 contributes directly to this architectural modernization effort.

Each migrated endpoint implemented during the project follows the command processing pattern described in this chapter. Across multiple Apache Fineract modules, legacy write operations were systematically replaced with typed request models, typed commands, dedicated handlers, updated service interfaces, and strongly typed response objects while preserving existing business functionality and maintaining compatibility with the existing REST APIs.
