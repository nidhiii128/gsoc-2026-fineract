= Legacy Command Processing Architecture

Before the introduction of the new Command Processing Infrastructure, Apache Fineract handled nearly all write operations through a centralized command processing mechanism built around the `JsonCommand` abstraction.

This architecture provided a common mechanism for processing create, update, delete, and state transition requests across different business modules. Although the approach successfully unified command execution, it relied heavily on generic request objects and runtime parsing, which became increasingly difficult to maintain as the project evolved.

== High-Level Architecture

The following diagram illustrates the legacy processing pipeline.

----
                HTTP Request
                     │
                     ▼
              REST API Resource
                     │
                     ▼
              JsonCommand Object
        (Generic JSON Representation)
                     │
                     ▼
          Business Service Layer
                     │
      ┌──────────────┼──────────────┐
      │              │              │
      ▼              ▼              ▼
 Parse JSON      Validate Data   Business Logic
      │              │              │
      └──────────────┼──────────────┘
                     ▼
        CommandProcessingResult
                     │
                     ▼
              HTTP Response
----

The REST resource simply forwarded the incoming request to the business service by constructing a generic `JsonCommand`. The business service was then responsible for interpreting the request and performing every subsequent step.

== JsonCommand

The central component of the legacy architecture was the `JsonCommand` object.

Instead of representing a specific business operation, `JsonCommand` acted as a generic container for all incoming request data.

A service receiving this object was expected to manually retrieve every required field from the underlying JSON payload.

Typical operations included:

* Reading string values
* Reading numeric values
* Reading boolean values
* Reading dates
* Reading nested objects
* Checking whether parameters were supplied
* Determining changed fields during updates

Because every endpoint received the same generic object, the compiler had no knowledge of the actual request structure.

== Responsibilities of Business Services

One of the primary architectural limitations was that business services were responsible for multiple independent concerns.

A typical service method performed the following sequence of operations:

. Extract request parameters from `JsonCommand`
. Validate request values
. Retrieve authenticated user information
. Perform authorization checks
. Execute business rules
. Update database entities
. Build a generic response object

This resulted in large service implementations that mixed infrastructure concerns with domain logic.

Instead of focusing exclusively on business behaviour, service classes also became responsible for request parsing and validation.

== Request Lifecycle

The execution flow of a typical write operation can be summarized as follows.

. A client submits an HTTP request.
. The REST resource creates a `JsonCommand`.
. The command is passed to the service layer.
. The service manually extracts request fields.
. Validation is performed.
. Domain objects are updated.
. Database changes are committed.
. A generic `CommandProcessingResult` is returned.
. The REST API serializes the response.

Every write endpoint followed approximately the same processing pattern regardless of the business domain.

== Validation Flow

Validation was primarily implemented inside service implementations after request parsing.

Typical validation included:

* Required fields
* Null checks
* Business rule validation
* Date validation
* Numeric constraints
* Duplicate entity checks
* Referential integrity checks

Although effective, validation logic was distributed across numerous service classes instead of being represented directly within the request model.

This increased duplication and reduced consistency across different APIs.

== Response Generation

Most write operations returned a `CommandProcessingResult`.

The response generally contained information such as:

* Resource identifier
* Command identifier
* Office identifier
* Client identifier
* Additional metadata

Since multiple operations returned the same response type, the API exposed very little semantic information about the specific operation that had been executed.

As a result, generated API clients also lacked strongly typed response models.

== Architectural Limitations

As Apache Fineract continued to grow, several limitations of the legacy architecture became increasingly evident.

* Generic request representation prevented compile-time validation.
* Request parsing was duplicated across multiple services.
* Validation logic was scattered throughout the codebase.
* Service implementations mixed infrastructure and business responsibilities.
* APIs exposed generic response objects instead of operation-specific models.
* Client code generation produced weaker type information.
* Architectural evolution became progressively more difficult.

These limitations motivated the development of the New Command Processing Infrastructure, which introduces strongly typed commands, dedicated request and response models, centralized command dispatching, and cleaner separation of responsibilities.
